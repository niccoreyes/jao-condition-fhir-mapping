# Project guidance for future agents

## Intent

This workspace makes the Condition worksheet in `FHIR MAPPING_DOH-PHIC-JAO-No-2021-002 - Dictionary.xlsx` auditable from **source concepts → reusable FHIR implementation patterns**. The workbook has 34 populated clinical rows in 13 sections; preserve each row and its section even when concepts repeat. The WHO-style Level 3 logical model describes source meaning independently of FHIR decisions. The crosswalk and Sankey then express proposed mappings and open questions. The Sankey is a valued one-page overview: **refine its connections/content rather than replacing its visual form** unless the user asks for a redesign.

## Working habits

- Start with the workbook/source logical model and compare `mindmap-index.json`, `build-condition-mindmap.py`, the main crosswalk (`condition-logical-model.html`), and `condition-row-profile-mindmap.html`. For PHCDI scope, also read `condition-phcdi-release01-scoping-review.md` and the original `PHCDI Release 01(Core Datasets).csv`: it is historical work by a different organization, a generic element/form inventory without a JAO crosswalk, demonstrated deployment or clinical validation. Compare the proposed FHIR path/profile disposition as the primary dialog axis against physical CSV element paths/definitions; show JAO row identity/definition secondarily. Use `compare_phcdi_paths.py` (algorithm version embedded in row JSON) for deterministic explicit component matching; preserve extension/slice identity, normalize only declared R4 choice forms, distinguish exact literal path, normalized R4 choice-base (type unproven), parent-carrier, partial gap, related nonmatch, unsupported extension/slice and unresolved proposal. Shared resource name alone counts as zero element overlap; never infer clinical equivalence from token overlap or definitions. Any Jev semantic/workflow signal is a separate advisory with probability/confidence and human routing; it must not alter deterministic status or assert authority. The per-row PHCDI similarity measure (`evaluate-phcdi-similarity-jev.py`) is the same kind of advisory: it judges documented meaning/workflow only over five ordered 0–100 bands, keeps full probabilities and confidence, routes low-confidence or none/weak/partial rows to human review, and never becomes clinical equivalence, approval or conformance. Preserve sidebar navigation and source-row deep links across pages.
- Separate **existing PH Core 0.2.0 artifacts**, **proposed derivatives/canonicals (not live URLs)**, **international examples**, and **unresolved gaps**. Do not claim profile conformance based on base R4 validation. Source terminology examples are not bindings; workbook Terminology Binding cells are empty.
- Model the meaning of an assertion: a Yes/No/unknown answer is not automatically a diagnosis; no Condition is not a negative answer. PWD registration belongs on Patient, encounter symptoms can be Observations, and mortality is proposed as an **Observation** in light of current MDI/VRDR. Keep certification/coding-stage and national policy decisions visible.
- **Always link the terminology source or the policy, inline, as you go** — every SNOMED CT/LOINC concept gets an authoritative link, and every data element gets a link to the current Philippine policy that requires or defines it (issuing body, date, version). Read the policy to enumerate its answer options before proposing any code; if a policy has no stable public URL, cite it by name rather than invent one. Never fill unknowns by inventing bindings, clinical facts, or PH canonical endpoints.
- Prefer exact, source-backed SNOMED CT/LOINC concepts when the **clinical meaning and workflow match**; distinguish question codes from answer/diagnosis codes, and record uncertainties. For example, for disability type, read the current PH PWD policy and list its permitted classifications rather than guessing from SNOMED alone.
- Validate candidate SNOMED CT/LOINC codes with `python validate-terminology.py`, which uses the public **HL7 FHIRsmith** server `https://tx.fhir.org/r4` as its primary authority (falling back to the community FHIRLab server) and records the code-system **version** and timestamp for every check. Report an unreachable server as unreachable; never claim a version that was not returned. This is a public check, not the Philippine national terminology service, and never a binding.
- Score the row mappings with `python evaluate-rows-jev.py`, which uses TypeSafe's **Jev** (System One `https://api.typesafe.ai/v1/systemone`) as five independent score questions per row — traceability, policy link, policy options, meaning, terminology — normalized and weighted in code, with low scores or low confidence routed to human review. Treat the composite as a ranking aid for this mapping, not as clinical truth, and store probabilities and confidence rather than a bare number.
- Rate presentation with `python evaluate-quality-review-design.py` for the score display, `python evaluate-modal-readability-jev.py` for modal scanability/action navigation, and `python evaluate-terminology-presentation-jev.py --layout-metrics terminology-presentation-layout.json` for the source-option/candidate table (independent Jev Score rubrics with narrow 0–4 dimensions, probabilities and confidence retained). For the latter, first open Excel row 4 in a desktop browser and run `agent-browser eval --stdin < tests/terminology-geometry.js > terminology-presentation-layout.json`; its pass gates require >=.75 overall, >=.75 layout score, and a full-width desktop table without horizontal scrolling. Also check narrow-screen contained scrolling, dialog focus, and accessibility in the browser. Iterate at most three evidence-backed rounds until the relevant presentation score is >=.75/pass and static, browser, and applicable terminology checks pass. Low mapping-row scores remain review flags, **not** a target to inflate without evidence. Show a 0–100 score with stated thresholds, a labelled verdict, and per-dimension bars; encode confidence visually (hatching for low confidence) rather than as raw decimals, reuse page tokens, avoid cards inside cards, and keep a complete accessible label. Jev judges described design, not rendered pixels: confirm geometry, contrast, keyboard and mobile access in a real browser. If Jev/evidence is unavailable, record a blocker and stop; never chase scores or invent codes.
- For project tasks where the user requests delegation, use authorized Pi subagents for small independent, bounded tasks; use Luna (DeepSeek v4.1 Flash only if its provider credentials work). Keep one writer per checkout; do not parallelize edits in the same checkout. On delegation/provider/infrastructure failure, stop dependent work and report the failure rather than silently bypassing delegation or changing the plan.
- Jev and other typed-score evaluations are narrow presentation/ranking signals only: retain probabilities and confidence, route uncertain/low scores to human review, and never treat scores as generated explanations, clinical truth, source verification, policy approval, or accessibility/pixel validation. Interpret score areas only through the fixed rubric and independently check cited source/policy/terminology evidence; stop and report if required evaluator evidence is unavailable.
- Preserve small, coherent reusable profile boundaries rather than making a profile per row or disease. Keep dates, time zones, event pairing, provenance and status semantics explicit. Document decisions and unanswered human-review questions.
- Edit the generator for generated index/transaction/embedded diagram data, regenerate, and run `python audit-condition-sankey.py`, `python validate-condition-transactions.py` and, for terminology changes, `python validate-terminology.py`. Re-run `python evaluate-rows-jev.py` after row content changes so `condition-row-evaluation-jev.md` and the dialog scores stay current. The advisory PHCDI similarity measure is refreshed with `python evaluate-phcdi-similarity-jev.py` (one System One request per row; 429/529 retry; fail-closed atomic write) before rebuilding, so the embedded per-row measure and the `#similarity-report` section stay current. On evaluator errors, preserve prior outputs and report the failure; never replace prior results with partial/error output. For source-model changes, first run `python jao-l3-prototype/build_logical_model.py`. For link-rendering changes, open the page in a browser and run `agent-browser eval --stdin < tests/sankey-geometry.js` at desktop/narrow widths and after filtering; the independent static audit cannot establish visible endpoints. Keep the pinned D3 libraries and notices in `vendor/` synchronized with the self-contained HTML. Verify row dialogs, filters and links when the UI changes. `condition-sankey-audit.md` records the latest connection/terminology rationale.

## Useful prompts to frame a new task

- “For this workbook row, what exactly is asserted, where does it occur in the source model, and what would distinguish a question, finding, diagnosis, registration field, or certified mortality statement?”
- “Is the target path an actual R4/PH Core element, a proposed extension/slice/profile, or an unresolved gap? What evidence supports the chosen coding and its processing stage?”
- “Which current Philippine policy enforces this element? Link it; list the permitted response options and compare candidate terminologies even when the workbook contains no code.”
- “If two source rows share a FHIR element, how will users still trace each one back to its original section and review decision?”
- “What was actually validated—base R4 syntax, IG-specific profile constraints, terminology membership, or clinical policy—and what still needs owner approval?”

This guidance is intentionally revisable. Update this file when project scope, evidence or approved requirements change; preserve intent and provenance rather than freezing today's UI or profile choices.
