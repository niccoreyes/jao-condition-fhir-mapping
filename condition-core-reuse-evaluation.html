FHIR R4 relationship paths

Condition.subject → PatientRequired in R4; PH Core restricts the target to PH Core Patient.
Condition.encounter → EncounterOptional in PH Core; a stricter encounter-diagnosis derivative is a proposal.
Encounter.diagnosis.condition → ConditionR4 also allows Procedure. Current PH Core Encounter FSH references base Condition, not PH Core Condition specifically.
Encounter.diagnosis.use / .rankOptional diagnosis role and rank on Encounter. “Complication” requires a defined role system if used.
Observation.subject → PatientRequired only in a proposed patient-focused derivative; base R4 and PH Core Observation permit 0..1 subject.
Observation.focus → ConditionR4 permits a focus reference if an assessment is specifically about a Condition; not required for every question.
Condition.evidence.detail → ObservationSupporting clinical evidence can refer to an Observation or another resource.
Condition.stage.assessment → ObservationMay link a formal assessment supporting a typed stage; no GOLD value set is implied.
Patient.extension:pwdDisabilityExisting PH Core Patient registration extension; not a Condition attribute.

PWD registration is not a Condition profile

Reuse PH Core Patient and its existing PWD extension rather than deriving a Condition to hold administrative status.

Existing + gap

Existing path
Patient.extension:pwdDisability.extension:disabilityType.valueCodeableConcept (type, Excel 4)
Missing path
Permanent disability Yes/No (Excel 5): no defined permanence flag in the existing complex extension.
Reusable choice
Define permanence on the Patient registration extension only if this is a persistent legal/administrative property. An episodic assessment may instead require Observation.

Approval gate: PWD policy owner defines permanence, attester, effective period, and explicit No versus unknown; a profile cannot invent these semantics.

Question-answer and symptom-finding pattern

A single shared Observation pattern may be useful if question codes, status, values and provenance are harmonized. Do not force every Yes/No into a Condition.

Candidate pattern
Excel 7Excel 29Excel 37Excel 48
Shared elements
Observation.status (1..1), Observation.code (1..1), subject for patient-focused exchange, and a suitable Observation.value[x]. Use QuestionnaireResponse for a form response not promoted to a clinical finding.
Condition bridge
When a clinician establishes a positive disease assertion, create a separate Condition and optionally link evidence. No Condition instance does not equal a No answer.
Reusable choice
Start with PH Core Observation. Add one optional PH question-answer derivative only if all four rows share the same answer semantics and search contract; subtype codes remain domain-specific.

Approval gate: Decide whether COVID case status, pre-eclampsia/PIH, TB status and “other symptom” are diagnoses, screening answers or observed findings; specify Yes, No, unknown and not asked.

Mortality is a downstream specification

Current VRDR 3.0.0 and MDI 2.0.0 model causes with Observations. Propose a PH mortality Observation; distinguish certifier-authored cause lines from later coded underlying causes before fixing terminology.

Out of Core scope
Excel 9Excel 10
Candidate content
Proposed Observation.code identifies the mortality assertion; Observation.valueCodeableConcept.coding carries a coded cause and .text preserves original wording when they describe the same assertion. Certification versus later coding needs resolution.
Not equivalent
Encounter.diagnosis.use = ADMDX/DISDX describes admission/discharge roles, not the certified underlying cause.
Reusable choice
Keep PH Core Condition general; develop a mortality Observation profile/document after certification stage, ordering and coding are defined.

Approval gate: Mortality authority decides underlying versus immediate/contributing causes, sequence, certifier and ICD-10-PH coding policy.

Encounter-linked diagnosis

One Condition derivative can cover both complication sections and diagnoses, provided they truly mean a clinician-asserted diagnosis for a visit.

Core candidate
Excel 17Excel 21
Profile contract
Condition.category includes encounter-diagnosis; Condition.code 1..1; choose whether Condition.encounter must be 1..1 for this workflow.
Encounter link
Encounter.diagnosis.condition references the Condition. Encounter.diagnosis.use carries a role only when a code system and value are governed.
Reuse boundary
Do not create a separate Condition profile for “complication.” A local role code, if approved, belongs in an Encounter terminology policy.

Approval gate: Are the two source blocks duplicates or different encounters? Is “complication” a diagnosis role, an adverse event, or a disease outcome?

Diagnosis assertion time

These are two source fields for one clinical timestamp, not two FHIR dateTime elements.

Semantic decision
Excel 23Excel 24
Use if asserted
Condition.extension with the standard http://hl7.org/fhir/StructureDefinition/condition-assertedDate, if source means when the clinician first acknowledged the diagnosis.
Use if recorded
Condition.recordedDate is when that Condition record was created in the system. Condition.onset[x] is when the illness began.
Reuse boundary
A shared time policy applies to both problem and encounter derivatives; no separate profile for date and time fields.

Approval gate: Define “diagnosed” as assertion, confirmation or entry time. If clock time is present, pair with date and offset; never manufacture midnight.

Longitudinal problem status

Reuse the problem Condition derivative rather than interpreting a form heading as a clinical status.

Registry qualifiers and COPD staging

Share the underlying Condition problem model, but keep registry-specific classification in a downstream module.

Domain policy first

Diabetes recency
“Newly diagnosed” is not equivalent to Condition.onset[x], recordedDate or assertedDate. An extension on Condition or a time-bound Observation is a candidate, not yet a defined artifact.
COPD stage
Two distinct Condition.stage repetitions could pair .type (grade vs group) with .summary; .assessment may reference supporting Observation. Do not treat GOLD grade as the whole Condition code.
Reuse boundary
Do not add GOLD editions or a diabetes-specific newness flag to a general PH Core Condition. Publish terminology and an optional registry derivative only after policy approval.

Approval gate: Define the “new” time window and reference event; specify GOLD edition (ABCD versus ABE), types, values and assessment date.

Evidence and decisions to validate

The source L3 model follows WHO's one-tab / one-model pattern; this architecture maps it to FHIR R4 and selected IG precedents. Workbook examples are not bindings.

Existing constraints checked

Current PH Core v0.2.0 FSH constrains Condition.subject to PH Core Patient and Condition.encounter to PH Core Encounter, while keeping Condition.code 0..1 and category 0..*. The existing PH Core Encounter FSH allows Encounter.diagnosis.condition to reference base Condition or PH Core Procedure and comments that PH Core Condition could be added later. A new Condition derivative cannot assume the Encounter profile already narrows this reference to it.

FHIR R4 defines Condition, Encounter and Observation with the element paths shown above.

Comparative precedents

US Core problems and encounter diagnosis split Condition by workflow. AU Core offers a broader single Condition floor. Current VRDR 3.0.0 and MDI 2.0.0 use mortality Observations; their US-specific certificate rules are not PH requirements.

Existing PH source: Condition FSH, Observation FSH, and PWD extension FSH.

Validation and ownership gates

Before release, approve semantic definitions with clinical, PWD, registry and mortality owners; define local terminology and binding strengths; produce FSH and examples; test the exact PH Core package with R4 4.0.1; and document CapabilityStatement/search obligations. A previous representative instance passed only a base R4 structural check, not these proposed profiles.
