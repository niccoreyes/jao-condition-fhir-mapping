# Scoping review: profiling FHIR `Condition` for the PH Core workbook use cases

**Scope:** the populated clinical rows in the workbook’s `Condition` sheet (34 source rows across 13 sections; 31 rows currently mapped to PH Core Condition, 2 to PH Core Patient, and 1 to PH Core Observation). The question is whether PH Core should define more specific Condition profiles and, if so, what kinds.

## Executive conclusion

**Yes—there is a sound precedent for additional PH Core Condition profiles, but profiles should be organized around distinct data-exchange purposes, not one profile per diagnosis name or workbook row.** The most compelling precedent is US Core: it deliberately separates longitudinal problems/health concerns from encounter diagnoses because they have different category, context, and search expectations. AU Core and IPS show how a shared Condition profile can establish a common floor for problem records. Specialty and mortality guides show that where meaning is unusually specific, a derivative profile may impose tighter terminology, provenance, timing, and workflow constraints.

PH Core Condition v0.2.0 is a useful general base, but its broad optionality is not enough by itself to standardize these workbook use cases: `category` is 0..*, `code` is 0..1, and the Condition profile’s code binding is an **example** binding. `subject` is 1..1 and constrained to PH Core Patient; `encounter` is optional. The profile has Must Support obligations for elements such as status, code, stage, and evidence, but its creator obligation is generally **MAY: able-to-populate**, while servers and consumers **SHALL: handle**. These obligations do not make the optional elements mandatory in an instance. [5]

A suitable PH Core design would establish a small set of workflow profiles—at minimum a problem/health-concern profile and an encounter-diagnosis profile—then add registry-specific constraints only where the source semantics, terminology, and exchange requirements are settled. Keep disability registration on Patient. Treat yes/no questionnaire items and observed symptoms as Observation or QuestionnaireResponse when that is what the source actually records. Model cause of death under a mortality-specific design, not as an Encounter diagnosis role.

### Common profile patterns

1. **A base profile is not a use-case contract.** Condition in FHIR R4 is deliberately broad: `code` and category are optional in the base resource, and the resource can represent a longitudinal problem, encounter diagnosis, health concern, or other clinical assertion. Profiles establish the common floor for a defined workflow. [11]
2. **Category carries workflow meaning.** `problem-list-item` and `encounter-diagnosis` are not interchangeable labels. A profile may require or slice categories so systems can search and display them consistently.
3. **Must Support is not the same as required cardinality.** Use minimum cardinality for values that must always be present; use explicit, actor-specific obligations for “populate if known,” “accept without error,” or display behavior. Do not use Must Support as a substitute for explaining these obligations.
4. **Terminology strength is a policy decision.** Example and preferred bindings do not create a closed list. Extensible bindings allow alternatives where the prescribed set has no suitable concept. National code systems must be identified by their canonical URIs; listing code examples is not a binding.
5. **Do not force questions into Condition.** A question such as “does the patient have X?” with a yes/no answer is a question response or finding, not necessarily a clinical assertion that X is present. Use Observation or QuestionnaireResponse for the question/answer. A positive clinical assertion can additionally be represented as Condition when appropriate. [11]

## Implications for PH Core and the workbook

### Recommended profile set

**1. PH Core Condition—Problem / Health Concern (derive from PH Core Condition).** Use for longitudinal problems, relevant history, and diseases that need management or registry tracking. Consider:
- Require `Condition.category` to include `problem-list-item` (or a PH-defined health-concern category only if governance agrees to define and publish it).
- Consider `Condition.code` 1..1 for the exchange. This requires the CodeableConcept element, not necessarily a `coding`; require `code.coding` separately if machine-readable coding is essential. Define any text-only legacy pathway explicitly.
- Retain `subject` as PH Core Patient. Keep `clinicalStatus` conditional in the FHIR manner: normally expected for managed problem-list items, but not a blanket mandatory value for every point-in-time diagnosis.
- Bind `Condition.code` to a governed PH value set with clear strength and version. The workbook’s terminology-binding cells are blank; SNOMED CT and ICD-10/ICD-10-PH entries are examples, not bindings. Decide whether the PH set is extensible and document how ICD-10-PH and SNOMED CT are coded/mapped.
- Define creator, server, and consumer obligations and search expectations separately from the data cardinality.

**2. PH Core Condition—Encounter Diagnosis (derive from PH Core Condition).** Use for a diagnosis asserted in a specific encounter, including complications when confirmed as encounter diagnoses. Require the `encounter-diagnosis` category and a coded `code`. If this profile means “diagnosis of this encounter,” make `Condition.encounter` mandatory (1..1); if historical diagnoses with optional encounter are in scope, keep it optional and document that scope instead. Put role/rank (e.g., primary, admission, discharge) on `Encounter.diagnosis` where applicable. Do not encode the underlying cause of death as admission/discharge diagnosis use.

**3. PH Core disease-registry profiles, selectively.** A generic problem profile can support hypertension, stroke, diabetes, COPD, TB, and COVID-19 where the assertion is a condition. Add a registry derivative only when it needs distinct minimum elements, value sets, or search/reporting behavior. For COPD, distinct `Condition.stage` repetitions can hold GOLD spirometric grade and GOLD symptom/exacerbation group, but the profile should identify each with `Condition.stage.type`, govern the allowed codes/values, and preserve the applicable GOLD version. For “newly or previously diagnosed diabetes,” first define the time window and the distinction from onset/recorded date; if necessary, define an extension or registry-specific element rather than infer it from `onsetDateTime` or `recordedDate`.

**4. PH mortality Observation profile or mortality bundle.** Use an Observation pattern for rows 9–10, following current MDI and VRDR. Decide whether row 9 is the certified Part I line or a subsequently manual/automated coded underlying cause; do not fix LOINC 69453-9, 80359-3 or 80358-5 without that answer. Associate the ICD coding in `Observation.valueCodeableConcept.coding` and verbatim description in `.text` when they refer to the same assertion; specify certifier/provenance, line ordering and national ICD system/version before authoring a PH profile. These US profiles are precedents, not Philippine conformance targets.

**5. Keep non-Condition destinations.** Keep disability registration on `Patient.extension:pwdDisability` and signs/symptoms on PH Core Observation when these are the intended meanings. If only a question response is captured, use QuestionnaireResponse or a question-coded Observation.

## Validation and evidence limitations

A representative Condition previously passed a base FHIR R4 structural validation (no errors; one narrative best-practice warning). That validates neither the proposed profiles nor the PH Core 0.2.0 constraints. The earlier remote HAPI validator could not resolve PH Core 0.2.0, the advertised canonical metadata endpoint returned 404, and the CI-build pages returned 404 on recheck. A local cache now contains `fhir.ph.core#current` with package version 0.2.0, but no new PH Core profile validation has been performed in this review. The v0.2.0 FSH source was checked at commit `3299879c369b49a306064e725de0b5f556512cd2`. Validate representative instances with the **versioned FHIR R4 core package and the exact PH Core 0.2.0 package** before claiming conformance.

This is a purposive scoping review, not an exhaustive survey or clinical policy determination. The PH Core comparison uses IG material retrieved earlier and the version-pinned FSH source linked below. Confirm all proposed rules with Philippine clinical and terminology stewards before publication.
