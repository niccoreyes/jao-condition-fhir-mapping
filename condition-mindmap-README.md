# Source-to-profile Sankey and transaction examples

Open [condition-row-profile-mindmap.html](condition-row-profile-mindmap.html#map). It connects **34** Excel clinical rows to **8 consolidated destinations** and **22 target subpaths** via **45 directed flows**. Shared profiles have one box with multiple subpaths; the proposed encounter, problem and COPD derivatives each have their own box. Unresolved destinations are explicitly marked as gaps. Selecting a row opens its use case, international IG comparison, a separate **historical PHCDI Release 01 comparison** (catalog element(s), CSV line and observed deviation—not clinical guidance), the current workspace recommendation and human-review question, and either a synthetic FHIR R4 transaction or an explicit modeling gap. Selecting a subpath shows all rows that share it. This is a proposed implementation mapping, not a published PH Core profile or an approved clinical policy.

## Provenance and reproducibility

- `build-condition-mindmap.py` joins the source logical-model index, the 34-row crosswalk, its reviewed IG discussions, and the row-specific proposal map. It writes `mindmap-index.json`, embeds the data and transactions into the standalone HTML, and creates **30** synthetic `Bundle.type=transaction` examples in `fhir-transactions/`.
- Rebuild: `python jao-l3-prototype/build_logical_model.py && python build-condition-mindmap.py`.
- Connection audit: `python audit-condition-sankey.py` (independent row/subpath expectations). In a browser, `agent-browser eval --stdin < tests/sankey-geometry.js` checks each rendered SVG endpoint against the row and path button borders. Decision rationale and terminology evidence: [condition-sankey-audit.md](condition-sankey-audit.md). Policy basis and policy-defined answer options per row: [condition-terminology-policy-review.md](condition-terminology-policy-review.md).
- Terminology check: `python validate-terminology.py` validates candidate SNOMED CT/LOINC codes against the public **HL7 FHIRsmith** server `https://tx.fhir.org/r4` (fallback: FHIRLab) and records the code-system version in `terminology-validation.json`. A version is only reported when the server returns one.
- Per-row quality review: `python evaluate-rows-jev.py` scores each row with TypeSafe **Jev** on five weighted dimensions and writes `row-evaluation.json`; the mind-map build embeds the result in each row dialog. Report and rationale: [condition-row-evaluation-jev.md](condition-row-evaluation-jev.md).
- PWD modelling: [condition-pwd-scoping-review.md](condition-pwd-scoping-review.md) compares Condition vs Observation vs Patient extension for disability, and how to attach the PWD identifier and permanence.
- PHCDI comparison: the row modal primarily compares the **current FHIR mapping path** with cited elements in the historical [PHCDI Release 01 CSV](PHCDI%20Release%2001%28Core%20Datasets%29.csv), with the original JAO source element as a secondary trace. [`compare_phcdi_paths.py`](compare_phcdi_paths.py) measures versioned component overlap (exact literal path, choice-base, parent carrier, gaps); [`phcdi-semantics-jev.json`](phcdi-semantics-jev.json) retains a separate, non-authoritative semantic advisory for all 34 rows. The [scoping study](condition-phcdi-release01-scoping-review.md) records source/deviation context. Neither structural overlap nor Jev establishes clinical equivalence, an approved PH Core profile or deployment.
- Advisory PHCDI similarity measure: `python evaluate-phcdi-similarity-jev.py` asks one Jev **Score** (five ordered 0–4 levels) and one **Noul** per row about how similarly the proposed mapping is represented in the cited historical PHCDI CSV, judging documented meaning and workflow only, and writes [`phcdi-similarity-jev.json`](phcdi-similarity-jev.json). The build attaches `phcdiSimilarity` to every row and embeds the generated summary block, so each dialog shows a compact 0–100 banded measure **beside but separate from** the deterministic structural badge, and the page adds an advisory **PHCDI similarity report** (`#similarity-report`) with all 34 rows sorted ascending, a band legend, a focusable scroll region and an explicit disclaimer. That report is filterable: labelled native controls above the table search the Excel number, JAO label, section, source ID, proposed FHIR path and cited PHCDI element, and select on similarity band, deterministic path status, human-review flag and sort order (similarity low→high default, high→low, workbook row order, confidence either direction), with a **Clear filters** button, a live `N of 34 rows shown` count, an empty-state row and a reset that restores all 34 rows. Filters intersect, apply only to the table, and never touch the generated `ROWS`/`PHCDI_SIMILARITY` blocks, the unfiltered all-rows summary, or the primary Sankey search/filter state. The measure is advisory only: it never changes the deterministic path status and does not assert clinical equivalence, conformance or approval.
- Design loop: `python evaluate-quality-review-design.py` rates the Quality-review presentation with Jev (0–100 ring, labelled verdict, dimension bars, hatched low-confidence bars) and iterates to a pass; results in `quality-review-design.json`. Row-modal scanability/action flow is separately judged by `python evaluate-modal-readability-jev.py`; [condition-modal-readability-review.md](condition-modal-readability-review.md) records the review and browser checks. Source-backed copy/redundancy is assessed with fixed-example Jev Scores by `python evaluate-modal-slop-jev.py`; [condition-modal-slop-review.md](condition-modal-slop-review.md) records the designer loop, citations and remaining low-scoring areas without claiming Jev generated explanations.
- Local checks: `python validate-condition-transactions.py`. All 30 passed the cached `hl7.fhir.r4.core#4.0.1` JSON schema, unique `urn:uuid` fullUrl checks, POST request URL checks, required structural fields and internal-reference resolution. Interactive similarity-report checks: `python -m unittest discover -s tests -p 'test_*.py'` and, in a browser, `agent-browser eval --stdin < tests/similarity-report-interaction.js` (controls, filters, sorts, reset, empty state, live count, row-detail modal/hash/focus) plus `tests/similarity-report-geometry.js` and `tests/sankey-geometry.js`.
- Representative Excel rows **4, 17, 29, 46, 49** were sent to HAPI baseR4 `Bundle/$validate` for a read-only validation operation. Each returned an OperationOutcome with **zero error/fatal issues**. Warnings included absent narratives/Observation performer/effective time, and an unknown PH PWD extension on the public server. This was not an execution of the transaction; no resources were committed.
- No example claims conformance to a proposed PH Core Condition derivative. The proposed profiles are not published, and ICD-10-PH / questionnaire / GOLD terminology bindings are not approved by the workbook.

## Link rendering

The page keeps its existing row/profile layout and highlight interactions. Curves use the [D3 Shape `linkHorizontal` generator](https://d3js.org/d3-shape/link) (pinned d3-shape 3.2.0 and d3-path 3.1.0, BSD-3-Clause; local copies and notices in `vendor/`). The builder inlines these into the HTML so the one-page view works offline. `d3-sankey` is not used because its node layout would replace the already-approved row/profile layout. The SVG is confined to the actual connection corridor; measured row-right and path-left anchors determine its link endpoints. When the layout changes, `ResizeObserver`/resize and filter renders redraw the paths. The independent audit checks membership; the browser test checks *visible geometry*.

## Deliberate non-examples

Excel **5** (disability permanence), **9-10** (proposed mortality Observation pending certification/coding-stage decisions), and **43** (newly/previously diagnosed diabetes) have no approved FHIR mapping/profile. A syntactically valid Bundle for them would not establish the requested clinical meaning. The diagram therefore displays the decision gate and **does not** fabricate a transaction.

All example clinical text, dates and local UUIDs are synthetic. Several examples use text-only CodeableConcepts to demonstrate R4 structure, not terminology interoperability. Excel 25 uses an illustrative ICD-10 coding; it does not bind the proposed PH profile or declare an ICD-10-PH system.
